Six-Person Team / Backend

FairTix

Java 21 / Spring Boot concert-ticketing prototype using PostgreSQL row locks, Redis waiting rooms, fraud checks, and verified payment webhooks. Runs locally; not production-deployed.

Hard part: preventing overlapping seat reservations under contention. Decision: lock Postgres seat rows in sorted ID order; use Redis for the queue and fraud-velocity signals, not seat ownership.

My part: the queue and fraud packages and substantial backend implementation across inventory, auth, and payments. Teammates are credited in the repo; Stripe support is off by default.

Recorded contention experiment: 200 hold requests from 200 users for 50 seats, drained by 9 to 20 concurrent workers on PostgreSQL 16, across four runs without a double-hold or double-sale. Read the test setup and results. Same-user purchase-cap and queue-capacity races were corrected in changes merged November 2026, using PostgreSQL advisory locks and forced-overlap integration tests. Multi-instance behavior remains untested.
